# Contributing to ScrollFlow

Thanks for stopping by. ScrollFlow is deliberately small — zero runtime dependencies, two files a person can read in one sitting — and the best contributions keep it that way.

## Getting started

```bash
git clone https://github.com/aqles/scrollflow.git
cd scrollflow
npm install   # only installs terser, a dev-only tool for the minified build
npm test      # smoke tests, no framework
npm run build # regenerates dist/ from src/
```

You do not need the build to try things out: the demo page (`index.html`) and everything in `examples/` load straight from `src/`.

## Making a change

1. Fork the repository and branch from `main`.
2. Change the source in `src/scrollflow.js` / `src/scrollflow.css`. Never edit `dist/` by hand — it is generated by `npm run build`, and `dist/scrollflow.esm.js` is generated from the classic script for the same reason.
3. If your change touches the parallax or progress maths, add or adjust an assertion in `test/smoke.mjs`. Those two helpers are pure functions on purpose.
4. Run `npm test` and `npm run build`, and open the demo page to check your change in a browser.
5. Open a pull request and say plainly what changed and why.

## Ground rules

- **No runtime dependencies.** Ever. That is the whole pitch of the library.
- **Keep the public API stable.** The `data-sf-*` attributes, the option names, and `refresh()` / `destroy()` are promises.
- **Mind the size.** If a change grows the gzipped total by more than a few hundred bytes, the pull request should say why it is worth it.
- **Reduced motion and no-JavaScript are features.** New effects need a story for both.
- Plain code over clever code. The next reader might be a beginner using this project to learn — that is a feature too.

## Reporting a bug

Open an issue with the browser, a small page that shows the problem (a single HTML file is perfect), and what you expected to happen.
